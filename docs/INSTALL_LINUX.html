Put the AI server on your Linux machine

This guide assumes you have never set up a Linux server. You will copy short commands into a terminal window, one at a time, and check a clear sign of success after each part.

Your server has a screen, so you can do everything with the mouse and keyboard on that machine. If you would rather work from your own computer, use SSH (step 1).

  • About 90 minutes
  • 60 GB free disk
  • Ubuntu 24.04
  • Intel Arc Pro B70
  • Models: step 7

0

Read this first

5 min

What you need

  • A machine running Ubuntu 24.04 LTS with an Intel Arc Pro B70 graphics card installed. This guide uses Vulkan through the open-source Mesa driver, so you do not install any Intel driver package. (NVIDIA cards would use CUDA instead; they are not covered here.)
  • The machine sits next to you with a monitor, keyboard and mouse. Everything is done on its own screen; no second computer is needed.
  • 32 GB of RAM or more, and about 60 GB of free disk. The helper models alone are about 20 GB.
  • A user account that may use sudo (run a command as administrator). Do not work as root: the application must run as a normal user.
  • Internet access on the machine, to download packages and models.

How to read the commands

  • Each black box is one command. Click Copy, paste it into the terminal (Ctrl+Shift+V in the Ubuntu terminal), press Enter, and wait until the prompt comes back before the next one. The $ in front of a box is not part of the command.
  • Anything in [SQUARE BRACKETS] is a value you replace with your own, brackets included, for example [REPO_URL], [USER], [SERVER_IP].
  • ~ means your home folder, for example /home/alice. When sudo asks for a password, type your own; nothing appears on screen while you type, which is normal.
  • The screens in this guide are drawings of what you should see, not photos. Yours will differ in small ways.

Before you install anything, open the BIOS once (press Del or F2 while the machine starts) and make sure Above 4G Decoding and Resizable BAR (sometimes called Smart Access Memory or Re-Size BAR Support) are enabled. Intel Arc cards run slowly or not at all without them. Save and exit.

Never paste real passwords, API keys or tokens into chat, tickets or documents. Every secret in this guide is a placeholder on purpose.

2 min

On the server's own screen

Press Ctrl+Alt+T. Or click Show Apps (the grid of dots at the bottom of the left bar), type Terminal, and click the icon.

From your own computer (optional)

Windows 10/11, macOS and Linux all include ssh. In PowerShell or a terminal on your computer:

ssh [USER]@[SERVER_IP]

The first time it asks "Are you sure you want to continue connecting?". Type yes, then your password.

Check where you are

whoami && lsb_release -ds && free -h | head -2 && df -h ~ | tail -1

You should see your user name (not root), Ubuntu 24.04..., your RAM, and your free disk space.

2

Install system programs

5 min

Refresh the package list, then install git, Python, the Vulkan graphics tools, the download tools, and the password store. The first command also brings the graphics firmware up to date.

sudo apt update && sudo apt full-upgrade -y
sudo apt install -y git curl wget unzip tmux python3 python3-venv python3-pip mesa-vulkan-drivers vulkan-tools pciutils linux-firmware gnome-keyring dbus-user-session

The Arc Pro B70 is a recent card (Intel's "Battlemage" generation). It needs a recent Linux kernel and Mesa. Ubuntu 24.04's optional newer kernel ("HWE") provides that:

sudo apt install -y linux-generic-hwe-24.04
sudo reboot

The machine restarts. Open the Terminal again (Ctrl+Alt+T) and continue.

The Python version must be 3.10 or higher:

python3 --version
3

Check the graphics card

3 min

First check that Linux sees the card and uses its driver. The kernel should be 6.14 or newer:

uname -r
lspci -nnk | grep -A3 -iE 'vga|display'

The Intel card appears, with the line Kernel driver in use: xe (or i915). Both drivers work with the steps below.

Then ask Vulkan, the interface llama.cpp uses, what it sees:

vulkaninfo --summary

If it says command not found, lists only llvmpipe (a slow software stand-in), or the card is missing from lspci:

  1. Re-check the BIOS settings from step 0 (Above 4G Decoding and Resizable BAR).
  2. Make sure the monitor is connected to the Arc card, or at least that the card is firmly seated and has its power cables plugged in.
  3. Check that the kernel is 6.14 or newer (uname -r). A brand-new card can need an even newer kernel and Mesa than Ubuntu 24.04 ships. Ask whoever supplied the hardware, or see the last step; do not carry on until the card is listed.
4

Get the application

3 min

Download the code from your company's repository. Ask the person who gave you this guide for [REPO_URL] and, for a private repository, for access (a deploy key or a token). Never paste a token into a shared document.

git clone [REPO_URL] ~/a770-dual-runtime
cd ~/a770-dual-runtime

Prefer clicking to pasting? The folder contains a small installer window that does steps 2, 3 and 5 to 12 for you with buttons, a progress list and a live log. Start it with this one command, and a page opens in the server's browser:

python3 docs/install_gui.py

It listens only on this machine, asks for your password in Ubuntu's own password window (it never sees it), and runs exactly the commands in this guide. Restart the machine when it asks you to, then run the same command again and carry on. To get the code onto the machine in the first place you still do steps 1, 2 and 4 by hand (git comes from step 2), or copy the folder from a USB disk.

From here on, run every command from this folder. If you close the terminal and come back, run the cd line again first.

5

Install the Python parts

5 min

This makes a private Python environment called .venv inside the folder. Nothing is installed system-wide.

python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip

Install the exact, checked versions:

.venv/bin/python -m pip install --require-hashes -r requirements.lock

If that fails with a hash error (the lock file was made on Windows), use the plain list instead:

.venv/bin/python -m pip install -r requirements.txt

The last line should say Successfully installed ....

6

Install llama.cpp and the helper programs

5 min

llama.cpp runs the language models. stable-diffusion.cpp makes images. The download tool fetches ready-made Linux builds from GitHub and unpacks them into ~/llama-vulkan and ~/sd-vulkan:

.venv/bin/python scripts/download_models.py --binaries --backend vulkan --bin-dir ~

Check that the engine starts and sees your card(s). It should list one device, the B70, as device 0.

~/llama-vulkan/llama-bench --list-devices

Want Intel's own SYCL engine as well? Finish this guide with Vulkan first. Step 16 installs SYCL next to Vulkan and step 17 shows how to switch between the two.

The automatic download failed? Do it by hand

Open github.com/ggml-org/llama.cpp/releases, copy the link of llama-<build>-bin-ubuntu-vulkan-x64.tar.gz, then:

wget -P ~/Downloads [LLAMA_RELEASE_URL]
mkdir -p ~/llama-vulkan && tar -xzf ~/Downloads/[LLAMA_ARCHIVE_NAME].tar.gz -C ~/llama-vulkan

The archive may unpack into a sub-folder. Find where llama-server ended up; that folder is your llama_bin_dir in step 9:

find ~/llama-vulkan -name llama-server

For the image maker, take the Ubuntu + Vulkan zip from github.com/leejet/stable-diffusion.cpp/releases and unpack it into ~/sd-vulkan the same way. Then make the programs runnable:

chmod +x ~/llama-vulkan/llama-server ~/llama-vulkan/llama-bench ~/sd-vulkan/sd-server
Build llama.cpp from source instead 
sudo apt install -y build-essential cmake libvulkan-dev glslc
git clone https://github.com/ggml-org/llama.cpp ~/llama.cpp
cmake -S ~/llama.cpp -B ~/llama.cpp/build -DGGML_VULKAN=ON && cmake --build ~/llama.cpp/build --config Release -j

The programs end up in ~/llama.cpp/build/bin. For NVIDIA use -DGGML_CUDA=ON.

7

Download the models

30-60 min

Models are large files, so this is the slowest step. Make the folders first. Any disk with enough space works; if you choose another path, remember it for step 9.

mkdir -p ~/Models/orchestrator/voice-models/tts ~/Models/orchestrator/image-models

What the tool downloads, and what you copy yourself

Large chat models are not downloaded by the tool. You copy those into ~/Models yourself (USB disk or the Files app; see "Copy from the Windows machine" below), one folder per model, as in the big table.

The tool fetches only the small helpers, about 3.5 GB in total: the Laya router (runs on the CPU), the embedder, the Whisper large-v3 speech-to-text model (3.1 GB), and the two spoken-reply voices. Files you already have are skipped, and an interrupted download resumes, so you can run it again.

.venv/bin/python scripts/download_models.py --small --models-dir ~/Models

Other groups are optional and left out on purpose: vision (image reader, 3.2 GB), routing (the Ornith 9B executor, 5.8 GB), image (image maker, 6.7 GB) and voice (Whisper turbo as well, plus both voices, 3.8 GB). Add any of them by name, for example ... download_models.py --small vision --models-dir ~/Models. Run the tool without options to see the list. The old Needle router is not needed: this setup uses Laya.

Choosing a chat model for the B70. The card has about 32 GB of video memory, shared by the main chat model, its context memory (which grows with long conversations) and every helper model that is loaded. As a rule, pick a main model whose file is 16 to 20 GB or less, for example Qwen3.8 27B Q4_K_M (16.8 GB) or Gemma 4 26B A4B (16.8 GB). Copy from the Windows machine (recommended for the large chat models)

If the Windows PC and the server are on the same network, copy a folder over directly. [WINDOWS_USER]@[WINDOWS_PC_IP] is a Windows account on that PC (it needs the optional Windows feature OpenSSH Server switched on). If the copy is interrupted, run it again.

scp -r "[WINDOWS_USER]@[WINDOWS_PC_IP]:/E:/AI/Models/Qwen3.8-27B" ~/Models/

A USB disk is simpler and more private: plug it in, open it in the Files app (it appears in the left bar), and drag the folders into ~/Models. Nothing crosses the network.

Download a single file by hand

wget -c resumes a broken download. Example for one chat model once you have its link:

mkdir -p ~/Models/[MODEL_FOLDER] && wget -c -P ~/Models/[MODEL_FOLDER] [MODEL_FILE_URL]

Some models ask you to accept a licence or sign in. If a download answers 401 or 403, open the model page in the browser, accept the licence, create a read-only access token in your Hugging Face settings, and add --header="Authorization: Bearer [HF_TOKEN]" to the wget command. Keep the token private.

Check the result

ls -lhR ~/Models | head -80

Every file should be as large as in the tables. A file of only a few kilobytes is an error page, not a model: delete it and download again.

Edit the settings

5 min

The file config/app.json still holds Windows paths such as E:/AI/Models. First let the downloader rewrite the paths it knows (files already downloaded are skipped):

.venv/bin/python scripts/download_models.py --binaries --backend vulkan --bin-dir ~ --models-dir ~/Models --write-config

List any Windows paths that are left:

grep -n 'E:' config/app.json

Open the file in a text editor. On the server's screen the easy way is the graphical editor:

xdg-open config/app.json

If the file opens in a web browser instead, use nano config/app.json in the terminal (Ctrl+O, Enter saves; Ctrl+X quits).

The values to check

  • "models_dir": /home/[USER]/Models
  • "common_dir": a folder for users' generated files and uploads, for example /home/[USER]/common (made in step 10)
  • "runtime": "vulkan", "cuda" for NVIDIA, or "sycl" after step 16
  • Under "runtimes" then "vulkan": "llama_bin_dir" is the folder that holds llama-server (step 6). Set "gpu_devices" to "auto" to use every card found, or to [0]. With one card, every GPU number in the settings must be 0.
"models_dir": "/home/[USER]/Models",
"common_dir": "/home/[USER]/common",
"runtimes": {
  "vulkan": { "llama_bin_dir": "/home/[USER]/llama-vulkan", "backend": "vulkan", "gpu_devices": "auto", "small_model_gpu": 0 }
}
10

Folders and permissions

2 min

The application runs as your normal user and must be able to write in its own folder, in common_dir, and in the model folders. common_dir can hold customer files, so keep it private to your user:

mkdir -p ~/common && chmod 700 ~/common

For a folder on another disk (under /srv or /mnt), create it once with sudo and give it to your user:

sudo mkdir -p [COMMON_DIR] && sudo chown "$USER":"$USER" [COMMON_DIR] && sudo chmod 700 [COMMON_DIR]
  • No other Linux account should be able to read common_dir or the *.db database files.
  • You do not need one Linux account per application user. The application separates users itself.
11

Password store

2 min

Cloud API keys and connector tokens go into the system keyring, never into a file. Check which keyring Python can use:

dbus-run-session -- sh -c '.venv/bin/python -c "import keyring; print(keyring.get_keyring())"'

The answer should contain SecretService.

If it says fail or keyrings.alt, stop and install gnome-keyring (step 2). Never install the package keyrings.alt: it keeps secrets in a plain text file.

12

First start

5 min

Start the application in the terminal so you can watch it. Replace [KEYRING_PASSWORD] with a new password you choose and store it in your company's password manager.

dbus-run-session -- sh -c 'printf "%s" "[KEYRING_PASSWORD]" | gnome-keyring-daemon --unlock --components=secrets && .venv/bin/python server_manager.py --port 8000'

The first start creates the databases and asks you to create the super-admin account. Type a user name and a strong password, and save the password in your password manager. Leave this terminal open.

Open it in the browser on the server

Open Firefox (or any browser) on the server and go to:

http://localhost:8000

From another computer on your network, use http://[SERVER_IP]:8000. That needs step 14 first. The server's address is shown by:

hostname -I

To stop the application, click the terminal and press Ctrl+C.

Unattended first start. Instead of the prompt, you can set the admin account through variables for that one run. The leading space keeps the line out of the shell history. Clear them afterwards.

 export A770_BOOTSTRAP_USERNAME=[ADMIN_USER] A770_BOOTSTRAP_PASSWORD=[ADMIN_PASSWORD]
unset A770_BOOTSTRAP_USERNAME A770_BOOTSTRAP_PASSWORD

Run only one copy of the application per machine: a second copy stops the running model servers.

What the first start creates for you

  • Databases: auth.db, projects.db, memory.db and usage.db appear in the application folder with all their tables. You copy nothing.
  • Roles and permissions: the two built-in roles, admin and user, and the full permission list are created automatically, and refreshed at every start, so updates add new permissions by themselves. The admin role gets every permission except a few that are deliberately never granted automatically. The user role gets the normal-user set. Your super-admin account becomes an administrator.
  • Your staff: accounts are not created for you. Add them afterwards in the application's admin settings; they receive the user role unless you change it.
  • Starter content: a few starter agents and the knowledge categories are added.

Lock the databases down once. The application does not set file permissions, so Ubuntu's default lets other accounts on the machine read them, and they hold chat history, documents and password hashes. Run this once after the first start (the installer window does it for you):

chmod 600 ~/a770-dual-runtime/*.db ~/a770-dual-runtime/*.db-*

If it says No such file for the second pattern, that is fine. Run it again after later restarts only if new database files appear.

Check the models

Open Settings then Models. Every .gguf file from step 7 should be listed. Check which GPU each helper model uses. The shipped file names GPU 1 and 2 from the original two-card PC; this machine has one card, so set every helper to GPU 0 (a GPU that does not exist is moved to the default one automatically, but set it anyway so the screen is honest). Enter your cloud API keys in Settings too.

13

Keep it running

10 min

A program started in a terminal stops when the terminal closes. Choose one of these.

Simple: tmux, a terminal that stays alive

tmux new -s a770

Run the start command from step 12 inside it. Then press Ctrl+B, let go, and press D. The application keeps running. Come back with:

tmux attach -t a770

Proper: a service that starts at boot

A service has no logged-in desktop, so the keyring password goes into a file only you can read:

mkdir -p ~/.config/a770 && (umask 077; printf '%s' '[KEYRING_PASSWORD]' > ~/.config/a770/keyring-pass)

Create the service file (replace [USER] with your user name). It is one command from sudo tee to the last EOF:

sudo tee /etc/systemd/system/a770.service > /dev/null <<'EOF'
[Unit]
Description=a770 AI server
After=network-online.target
Wants=network-online.target

[Service]
User=[USER]
WorkingDirectory=/home/[USER]/a770-dual-runtime
ExecStart=/usr/bin/dbus-run-session -- sh -c 'gnome-keyring-daemon --unlock --components=secrets < /home/[USER]/.config/a770/keyring-pass && exec /home/[USER]/a770-dual-runtime/.venv/bin/python server_manager.py --port 8000'
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable --now a770

Afterwards you can check, watch the log, or restart it:

systemctl status a770
journalctl -u a770 -f
sudo systemctl restart a770

The service must run as your normal user, never as root. Do not switch on ProtectHome or ProtectSystem=strict unless you list the application, model and common_dir folders under ReadWritePaths=. Press Ctrl+C to stop watching the log.

14

Firewall and access

5 min

By default the application listens only on this machine. To reach it from other computers, add --host 0.0.0.0 to the start command (step 12 or the service file) and allow the port only from your office network. Allow SSH first, or you can lock yourself out:

sudo ufw allow OpenSSH
sudo ufw allow from [LAN_SUBNET] to any port 8000 proto tcp
sudo ufw enable

[LAN_SUBNET] looks like 192.168.1.0/24.

Data protection. The application stores chat history, uploaded documents and password hashes. If it can be reached from outside this machine, put TLS (HTTPS) in front of it with nginx or Caddy.

Card numbers in chats are masked by the application, but the databases can still hold sensitive data. Move them only over encrypted channels such as scp, keep them private with chmod 600 ~/a770-dual-runtime/*.db, and follow your PCI-DSS and Bangladesh Bank data-handling rules.

16

Use Intel's SYCL engine (optional)

45 min or more

Step 6 installed the Vulkan engine. SYCL is Intel's own compute engine for Arc cards. It is installed next to Vulkan, never over it: the Vulkan folder is not touched, and you choose one engine each time the application starts (step 17). Do this step only after the Vulkan setup works.

Tested with Ubuntu 26.04, Intel oneAPI 2026.x, llama.cpp b10840 and three Intel Arc Pro B70 cards. Other combinations may need other package names or settings. SYCL needs the application branch sycl_support_v3 (or newer): older versions do not know the sycl engine.

1. Get the SYCL version of the application

cd ~/a770-dual-runtime && cp config/app.json config/app.json.before-sycl
git fetch origin && git switch sycl_support_v3 && git pull origin sycl_support_v3

The first command keeps a copy of your settings. It is also your way back (step 17).

2. Add Intel's package sources

Ubuntu does not carry the SYCL compiler or Intel's newest GPU driver. Add Intel's two package sources: one for the GPU driver, one for the oneAPI compiler.

sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://repositories.intel.com/gpu/intel-graphics.key | sudo gpg --dearmor -o /etc/apt/keyrings/intel-graphics.gpg
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/intel-graphics.gpg] https://repositories.intel.com/gpu/ubuntu $(lsb_release -cs) unified" | sudo tee /etc/apt/sources.list.d/intel-gpu.list
curl -fsSL https://apt.repos.intel.com/intel-gpg-keys/GPG-PUB-KEY-INTEL-SW-PRODUCTS.PUB | sudo gpg --dearmor -o /etc/apt/keyrings/oneapi.gpg
echo "deb [signed-by=/etc/apt/keyrings/oneapi.gpg] https://apt.repos.intel.com/oneapi all main" | sudo tee /etc/apt/sources.list.d/oneAPI.list
sudo apt update

Check that apt now knows every package we need. Each one must show a version after Candidate::

apt-cache policy libze-intel-gpu1 libze-dev intel-oneapi-compiler-dpcpp-cpp intel-oneapi-dnnl-devel intel-oneapi-mkl-devel | grep -E "^[a-z]|Candidate"

If a package shows Candidate: (none), stop. Intel may not publish it for your Ubuntu release, or the address changed: use Intel's current Linux GPU and oneAPI instructions. Do not add the repository of a different Ubuntu release: mixing releases can break apt and the GPU driver. The addresses above worked on the tested server.

3. Install the packages

sudo apt install -y git cmake ninja-build build-essential pkg-config intel-level-zero-gpu libze-dev intel-oneapi-compiler-dpcpp-cpp intel-oneapi-dnnl-devel intel-oneapi-mkl-devel

The download is large. Some names you may see elsewhere do not work or are not needed here: level-zero does not exist (the loader comes with the driver), and clinfo and intel-opencl-icd are not needed because this engine uses Level Zero, not OpenCL. The oneDNN package is ...dnnl-devel, with two l.

4. Let your user use the cards, and check that they are visible

sudo usermod -aG render,video [USER]

Sign out and in again (or restart), then:

ls -l /dev/dri/renderD*
source /opt/intel/oneapi/setvars.sh --force && sycl-ls

Every Arc card must appear as a [level_zero:gpu] line. If one is missing, fix the driver or the permissions first: the build cannot fix that.

5. Build the engine

Do this as your normal administrator user, and in one terminal window from start to end: the oneAPI settings exist only in the window where you ran source. First part, ending with the configuration:

mkdir -p ~/build && cd ~/build
git clone --branch b10840 --depth 1 https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
source /opt/intel/oneapi/setvars.sh --force
DNNL_DIR="$(dirname "$(find /opt/intel/oneapi/dnnl -name dnnl-config.cmake | head -n 1)")"
MKL_DIR="$(dirname "$(find /opt/intel/oneapi/mkl -name MKLConfig.cmake | head -n 1)")"
RPATH="$(echo "$LD_LIBRARY_PATH" | tr ':' '\n' | grep /opt/intel/oneapi | paste -sd';' -)"
RPATH="$RPATH;$(dirname "$(dirname "$DNNL_DIR")");$(dirname "$(dirname "$MKL_DIR")")"
echo "DNNL_DIR=$DNNL_DIR"; echo "MKL_DIR=$MKL_DIR"; echo "RPATH=$RPATH"
cmake -S . -B build-sycl -G Ninja \
  -DGGML_SYCL=ON -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=icx -DCMAKE_CXX_COMPILER=icpx \
  -DDNNL_DIR="$DNNL_DIR" -DMKL_DIR="$MKL_DIR" \
  -DCMAKE_BUILD_WITH_INSTALL_RPATH=ON \
  -DCMAKE_BUILD_RPATH='$ORIGIN;'"$RPATH" \
  -DCMAKE_INSTALL_RPATH='$ORIGIN;'"$RPATH"

The three echo lines must show real folders, and the configuration must end without any Error or a warning about Level Zero, DNNL or MKL. If it does, see "If something fails" (step 18) before building.

The build itself is the long part:

cmake --build build-sycl --target llama-server llama-bench -j

A screenful of 'barrier' is deprecated warnings and the line UI: download dist.tar.gz ... failed are harmless. The "run path" in the configuration lets the programs find their own libraries and oneAPI's, without changing the settings of any other program.

6. Test the build before installing it

cd ~/build/llama.cpp/build-sycl/bin && ldd ./llama-server | grep -c "not found"

The number must be 0. The engine also needs two oneAPI memory-library folders in the environment of whatever starts it. Find their version numbers:

ls /opt/intel/oneapi/umf /opt/intel/oneapi/tcm

The tested server showed 1.2 and 1.6. Use your numbers in place of [UMF_VERSION] and [TCM_VERSION] (stay in the same folder):

ONEAPI_DEVICE_SELECTOR=level_zero:gpu LD_LIBRARY_PATH=/opt/intel/oneapi/umf/[UMF_VERSION]/lib:/opt/intel/oneapi/tcm/[TCM_VERSION]/lib ./llama-bench --list-devices

Every card must be listed, as SYCL0, SYCL1 and so on, each with its memory.

7. Install it next to Vulkan

mkdir -p ~/llama-sycl && cp -a ~/build/llama.cpp/build-sycl/bin/. ~/llama-sycl/
ldd ~/llama-sycl/llama-server | grep -c "not found"; ldd ~/llama-sycl/llama-bench | grep -c "not found"

Both numbers must be 0. Keep the whole folder together: the programs load the libraries stored beside them. Do not change ~/llama-vulkan.

8. Add the engine to the settings

Open config/app.json (step 9 shows how). Inside "runtimes", next to "vulkan" (put a comma after the Vulkan entry), add:

"sycl": {
  "llama_bin_dir": "/home/[USER]/llama-sycl",
  "backend": "sycl",
  "gpu_devices": "auto",
  "small_model_gpu": 0,
  "env": {
    "ONEAPI_DEVICE_SELECTOR": "level_zero:gpu",
    "GGML_SYCL_ENABLE_VMM": "0"
  }
}

Leave "runtime": "vulkan" as it is for now: you switch in step 17. Check that the file is still valid:

python3 -m json.tool config/app.json > /dev/null && echo "json ok"

Two settings on the tested build matter:

  • "GGML_SYCL_ENABLE_VMM": "0" is needed. Without it, a long message to a large model made the model server stop with GGML_ASSERT(ptr == ... pool_addr + pool_used). Short messages worked, so a quick "hi" test does not show the problem.
  • Do not add SYCL_CACHE_PERSISTENT or SYCL_CACHE_DIR. With this build they made the model server crash while loading (exit code -11). Also leave ZE_AFFINITY_MASK unset: it can hide cards from a split.

9. Start it on SYCL once, and test

Stop the running application first (loaded models stop with it). Then start it with the engine chosen for this start only:

cd ~/a770-dual-runtime && LLAMA_RUNTIME=sycl LD_LIBRARY_PATH=/opt/intel/oneapi/umf/[UMF_VERSION]/lib:/opt/intel/oneapi/tcm/[TCM_VERSION]/lib .venv/bin/python server_manager.py --port 8000

The start-up lines must contain runtime=sycl backend=sycl and list your cards as devices, for example [0, 1, 2].

Open the web page, then in Model Config set the tensor split to one number per card (1,1,1 for three cards, 1,0,0 for the first card only), press Apply and load a model. In the terminal the launch line must contain -dev SYCL0 (not Vulkan0). Then send a short message and a long one (paste a few pages of text). Both must be answered.

Run a Vulkan test too before you rely on this machine: step 17 shows how to go back for one start.

5 min

The application uses one engine per start. Switching is a change in the settings plus a restart: nothing is rebuilt or reinstalled, and both engine folders stay as they are. Stopping the application unloads every model, so switch when nobody is using it.

Try the other engine for one start

A LLAMA_RUNTIME in the environment wins over "runtime" in the file, and only for that start. Stop the application, then for SYCL:

cd ~/a770-dual-runtime && LLAMA_RUNTIME=sycl LD_LIBRARY_PATH=/opt/intel/oneapi/umf/[UMF_VERSION]/lib:/opt/intel/oneapi/tcm/[TCM_VERSION]/lib .venv/bin/python server_manager.py --port 8000

or for Vulkan (no oneAPI folders):

cd ~/a770-dual-runtime && LLAMA_RUNTIME=vulkan .venv/bin/python server_manager.py --port 8000

The next normal start uses the file's setting again.

Make SYCL the default (Vulkan to SYCL)

  1. Stop the application (in tmux: Ctrl+C; as a service: sudo systemctl stop a770).
  2. In config/app.json set "runtime": "sycl", then check the file: python3 -m json.tool config/app.json > /dev/null && echo "json ok"
  3. Give the starting process the oneAPI folders. In a terminal, use the command above without LLAMA_RUNTIME. For the service, add them in an override (it opens an editor): 
    sudo systemctl edit a770

    and put these two lines in it:

    [Service]
Environment=LD_LIBRARY_PATH=/opt/intel/oneapi/umf/[UMF_VERSION]/lib:/opt/intel/oneapi/tcm/[TCM_VERSION]/lib

    With PM2, export the same variable in your shell and run pm2 restart [APP_NAME] --update-env.

  4. Start it again and check the start-up line (runtime=sycl). Then re-save each model's settings (see below).

Go back to Vulkan (SYCL to Vulkan)

  1. Stop the application.
  2. In config/app.json set "runtime": "vulkan" and check the file as above.
  3. Start it the way you did before step 16: without the oneAPI LD_LIBRARY_PATH. For the service, remove the override: 
    sudo systemctl revert a770

    With PM2, restart from a shell that no longer has the oneAPI folders in LD_LIBRARY_PATH, using --update-env.

  4. Check the start-up line (runtime=vulkan) and that a model's launch line shows -dev Vulkan....

Quick way back: cp config/app.json.before-sycl config/app.json restores the settings from before step 16 and puts "runtime" back to Vulkan. It also removes every other change made to that file since then.

What is different between the engines (check after every switch)

  • Model settings are saved per engine. GPU layers and tensor split saved while Vulkan ran are not used by SYCL: the model starts with defaults until you save its settings once while SYCL is active (Model Config, Apply). The same is true the other way round.
  • The tensor split needs exactly one number per card. 1,1,1 for three cards, 1,0,0 for the first card only. With a different count the application writes tensor_split '1' has 1 entries but 3 GPUs are in use and uses an equal split over every card.
  • Card numbers may not match. Compare ~/llama-vulkan/llama-bench --list-devices with the SYCL list from step 16.6. The helper models' "gpu" numbers and "small_model_gpu" refer to these numbers.
  • Helpers share the cards with the main model. A main model split over every card leaves less memory for the helpers on the same cards. If a helper or the main model stops with exit code -11 while loading, look for a forgotten copy that holds a card: pgrep -af llama-server.
  • Speech and image helpers are separate programs with their own GPU number. After a switch, press Load on each one you use and check that it starts.
